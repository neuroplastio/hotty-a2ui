# 2026-10-09.10 — KIT-08c: HottyKeyHints

The fifth phase-1 leg: bubbles' help line, held against the help under
bubbles' list (`make shot NAME=list`, short and full). The short line
matches it in words, separators and its three dimming steps. The full
view splits its columns as bubbles' does.

**The catalog** (profile §6.10, instruction 10):
- `HottyKeyHints` has `toggle` (default true) and `weight`. The agent
  places it once; it follows the keyboard by itself.
- A HottyShortcut's `label` is what it lists. An unlabelled shortcut
  stays out.

**The view** builds the hints (`Controller.KeyHints`), so both renditions
show the same words:
- the focused component's keys, in bubbles' wording (`↑/k up`,
  `/ filter`, `enter choose`, `enter submit` in a HottyForm,
  `space toggle`, `enter press`), then `esc close` while a Modal is open;
- the labelled HottyShortcuts, keys written as bubbles writes them
  (`ctrl+s`, `alt+←`, `pgdn`; `view.KeyText`);
- `? more` while `toggle` is on.
- The full view: the component's keys in one or two columns (a list's
  moves, then its filter and Enter; a field's moves, then its edits),
  the shortcuts, then `tab next`, `shift+tab back`, `? close help`.
- A field's keys come from its resolved keymap, the surface's
  (TerminalKeys by default) with the components' over it, two keys an
  action at most. A one-line field leaves out line up, line down and
  newline, as bubbles' textinput does.
- `?` switches the views (`State.FullHints`, shared by the renditions)
  when nothing else took it. A field and a list's filter type it.
- The Table also takes k, j, g and G now, as bubbles' table does (the
  open point from .9).

**Cells:** keys in `muted`, what they do in `muted` faint, separators in
`border` faint. The Terminal theme's muted and border are the same SGR
90, so without faint all three were one grey. The line cuts as bubbles'
does, with ` …` where it fits. A HottyKeyHints always has a blank row
before it, as bubbles' help sits under its list.

**HTML:** a `kbd` for each key, the same colours and a grid for each
column. One rule differs from cells:
- A host moves focus among the elements it works itself (fields, boxes,
  Buttons) without telling the renderer. A live run in headless
  hottyterm showed the cost: after Tab moved from Title to Body, the
  line still said `enter submit`, which is wrong in a long text.
- So on a host, the component part shows only for a Table, a HottyList,
  a Slider or a select, whose keys go to the program. That matches the
  program's own key routing, so it is never a guess.
- Following the host's focus for the rest is KIT-08h. Static `:has()`
  matches in Blitz (`hotty render`); whether it restyles on a focus
  change is unprobed. The other way would be a host that says which
  element took focus, a SPEC change and so the maintainer's call.

**Text:** says nothing; a pipe takes no keys.

**Checked:**
- Tests: view, cells and html.
- `make shot NAME=list` (focused), plus a hand-made tape for both full
  views (VHS has no `?` key command, so `make shot` can't press it).
- `hotty render` of the HTML, short and full.
- Live in headless hottyterm, side by side: Tab moved the cells hints;
  `?` opened and closed the full view on the host.
- The rig's `wtype -M shift -k question` arrives as `Shift+Escape`. Type
  `?` as text (`type:?`) instead.

For the maintainer to judge:
- the help line flush left: bubbles' list indents its help with the
  list, while the kit's sits at the column edge, as Buttons and Text do;
- `tab next` and `shift+tab back` in the full view, which bubbles' list
  lacks and huh's forms have;
- the host rule above, and whether KIT-08h should chase the host's focus
  or wait for the SPEC.
