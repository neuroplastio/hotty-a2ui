# 2026-10-10.26 — KIT-16c: Confirm, a pattern of Buttons

KIT-16 asked for huh's Confirm in cells, "or a story showing it as a
pattern of Buttons". It is a pattern: no component, two stories under
Components, `hotty/confirm` ("Delete 3 files?") and `hotty/confirm-form`
(a HottyForm that ends in "Create the repository?"), catalog instruction
24, profile §6.24.

**Why a pattern.** huh's Confirm does two jobs.
- **A yes or no kept in a form**, which the user sets and changes. The kit
  already has it: `hotty/form` holds huh's "I accept the terms" Confirm
  against a CheckBox, and `hotty/switch` holds huh's inline Confirm
  against a HottySwitch (2026-10-10.5).
- **A question answered at once** (`huh.NewConfirm().Run()`): the answer
  is an action, which is what a Button is. A2UI's own example 10
  (notification permission) asks so, with Yes and No Buttons.

Existing pieces reach huh's behaviour:
- y and n: a HottyShortcut each, whose `press` is Yes or No;
- ← and → between the two: a HottyShortcut each, whose action calls
  `hottyFocus` with Yes or No;
- Enter picks: a focused Button presses on Enter (and Space);
- the picked one filled: Buttons are filled since 2026-10-10.16, the one
  with the keyboard reversed in the accent and the other on the grey, as
  round 1's huh boxes were. `autofocus` on No is huh's false.

A component would be a third boolean control beside the CheckBox and the
HottySwitch. It would bring questions the maintainer would have to settle:
- how a kept answer shows once the keyboard leaves, where `accent` is
  focus's and a switch's on (§3.6);
- whether Enter goes on, as huh's does, or submits, as the kit's fields do.

It would also be a new name for agents to learn for what basic's Buttons
already do.

**What the pattern can't do**, and a component could:
- Scope the keys to the question. HottyShortcuts are the surface's, so a
  surface asks one question so. y, n and the arrows answer from a Button
  elsewhere, a CheckBox or a HottySwitch too; a text field keeps them
  (§3.7). Per-component shortcuts are NEIO-11's open question 4.
- Keep the answer drawn once the keyboard leaves. Both Buttons are grey
  then, where huh keeps its answer filled.

**The reference.** `ref/gaps.go`: `confirm`, huh's Confirm alone with the
story's title and description, and `confirm-form`, a huh form of a Note,
two Inputs and the Confirm. Commands:
`make shot NAME=confirm` with `KIT_KEYS=` `COLS=64` `ROWS=10`, and
`NAME=confirm-form` with `REF_KEYS='Tab Tab'` `KIT_KEYS='Tab Tab'`
`ROWS=16`. Where they differ:
- huh pads its buttons two columns each side and centres them under the
  question; the kit's Buttons are padded one column (the look settled in
  2026-10-10.16) and start at the left.
- huh has a blank row between its description and its buttons. The kit
  has none: a control after a Text that is not a heading has no blank
  row (§3.3). Left alone; see the proposals.
- The help lines match, `←/→ toggle • enter submit • y Yes • n No` against
  `enter press • ←/→ move • y yes • n no • ? more`.
- In the form, huh's question is the Confirm's title at the end. The
  kit's heads the form: a Text after a field gets no blank row and would
  read as the field's note, while a heading over fields, and Buttons
  after them, are set apart (§3.3).

**The key hints**, both found by the stories (view/hints.go, profile
§6.10):
- **Same label, one hint.** HottyShortcuts with the same label are one
  hint, their keys joined by `/`, as a bubbles binding of several keys
  shows them: `←/→ move`.
- **A field's own keys are left out.** While a text field has the
  keyboard, a HottyShortcut whose key the field takes (a character it
  types, a key its keymap binds to an edit) is left out, since the key
  never reaches it (§6.1). In the form, Name showed `←/→ move • y yes • n
  no` while those keys typed and moved the caret.

**The host** (kit.css, profile §2). A focused Button had only the host
stylesheet's 1px `:focus-visible` ring (SPEC §8), which a rounded edge can
lose at a fractional scale (2026-10-10.5). The picked answer barely
showed. Now a Button with the host's focus is filled with `--k-focus`, its
label in `--k-on-accent`, as cells reverses it in the accent. This applies
to every Button on a host, not only these two. A List's row (`k-item`)
keeps its ring.

**The arrows on a host.** A host scrolls with the arrows a focused button
leaves (SPEC §5.3), so the Row carries `keys`
`ArrowLeft=program ArrowRight=program`. Its `data-keys` gives them to the
program from the Buttons inside (SPEC §10.2, *Keys for the program*).
The code always did this for any component. The docs said `keys` was only
for text fields, and now say what a `program` binding does inside: the
catalog's extension description and profile §6.5.

**Text:** the question, then `[ Yes ]  [ No ]`.

**Open, for the maintainer** (proposals):
- **The focus fill on hosts.** Every Button on a host is now filled in the
  focus colour while it has the focus. Proposed to keep, as cells' look.
  It is not yet checked live on hottyterm.
- **A blank row before Buttons after text.** A Row of Buttons after a
  Text that is not a heading could take a blank row, as huh's dialog has.
  This goes with round 2's question about a blank row between stacked
  Rows of Buttons (2026-10-10.16). It would change A2UI's example 10 and
  others, so it is left for a look.
- **A HottyConfirm after all.** Worth building only if keys scoped to the
  question, or an answer kept and drawn huh's way, are wanted. The first
  could instead come from NEIO-11 question 4.
- **Left out of the stories:**
  - huh's h and l, and Y and N: four more HottyShortcuts;
  - the labels are `yes` and `no`, lower case as the kit's own hints are,
    where huh writes its buttons' `Yes` and `No`.
- **KIT-16h** ("the same" on a host) is what the baseline draws now.
