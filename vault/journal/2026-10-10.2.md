# 2026-10-10.2 — KIT-09c: HottyTree

The ninth phase-1 leg, and the first of the storybook revamp the
maintainer approved (2026-10-10): its nav is to be a tree. The reference
is bubbles' tree (`charm.land/bubbles/v2/tree`), `make shot NAME=tree`
with `REF_KEYS` eight Downs and `KIT_KEYS='Tab Tab'`.

**The catalog** (profile §6.14, instruction 14): `HottyTree` has `items`,
nodes of a `label`, an `icon`, a `value` and `children` (`$defs.treeNode`,
recursive); `selected`; `expanded`; `filter`; `onActivate`; `height`;
`emptyText`; and `weight`. A node's id is its value, else its place,
`0.2.1`.

**The view** (`view/tree.go`): the nodes in pre-order, those that show,
and the window a height shows, as a list's. Choices:
- `expanded` bound is written as the user folds; a literal is only the
  start, and the folding is then `State.Open`'s.
- The selection's branches show open whatever `expanded` says, so an
  agent reveals a node by selecting it. Moving the selection writes them
  into `expanded`, so they stay open behind it.
- Closing the branch the selection is in selects the branch.
- `filter` is a DynamicString, not the renderer's state as a list's
  filter is: bound to a TextField's path, it's a filter field over the
  tree, and the agent sees it. A node shows when it matches
  (sahilm/fuzzy), leads to a match, or is inside one; every branch shows
  open, in tree order.
- A node's guides take its siblings among those that show, so a
  filtered tree's lines end at its last match.
- `ClickNode` is the click rule both renditions share.

**Cells:** a row a node, two columns in. lipgloss's guides in `border`
(`├── `, `└── `, `│   `, the gap analysis's); bubbles' `▶ `/`▼ ` folds
in `muted`; a closed branch's count in `muted`; a root leaf's two blank
columns, so the roots line up. The selected node has the list's `│` bar,
and is bold in the accent while the tree has the keyboard, as bubbles'
is. Differences from bubbles', on purpose:
- several roots, since A2UI's `items` is a list (bubbles' has one);
- the bar, not bubbles' `→` cursor, as the list has it;
- the counts, as cells draws no icons: few have a glyph a column wide.

The first shot had `├─ ` guides three columns wide and the small `▸`/`▾`,
which were faint beside bubbles'.

**HTML:** a `role=tree` box, a `role=treeitem` row a node with
`aria-level`, `aria-expanded` and `aria-selected`, indented `--k-5` a
level. A fold column (`▸`/`▾`, blank on a leaf), the node's icon (blank
where others have one, so labels line up), the label. The selected row
is the list's. Its `data-keys` are the list's; letters and Enter come
anyway. `.k-fold` was the diff's already: the tree's is `.k-node-fold`.

**Text:** cells' rows, `> ` on the selected one.

**A fix on the way:** a host sends a text field's `change` as it commits
the field, when its focus leaves it, often for where the renderer just
moved the keyboard (`a=focus t=…`). `Event` took that `change` as "the
keyboard is here", so the program thought the field had it while the
host had the tree, and the tree's keys were lost. Now only `input`, or a
control's `change` (which comes at once), says where the keyboard is
(profile §2, the keyboard). The tree's vector found it.

**A gap, reported to hotty:** Tab on a host moves focus where the
program doesn't see it (SPEC §9), and keys bound to `program` come as
terminal input, with no element. So after the user Tabs into a box (a
Table, a HottyList, a HottyDiff, a HottyTree), its keys go to the
element the renderer last knew, and do nothing. A click makes it work.
The vectors give the box focus (`focus:`), as the list's and the table's
do. KIT-08h has the same root.

**Checked:** `make check`; the vector in both renditions; the story
rendered by `hotty render` in terminal and material light; the cells
side in a pty and in the shot.

**After the maintainer's first look** (1ee9c8e):
- "The scroll wheel doesn't scroll the tree." In cells, the wheel only
  scrolled HottyScrollViews; now a tree with a height takes it first,
  three rows a notch, and leaves the selection. The rows follow the
  selection only when it moves (`State.Revealed`), so the wheel can
  take it out of view and a key brings it back. On a host the windowed
  rows couldn't scroll at all: the tree with a height is now a box the
  host scrolls (SPEC §5.3), and its selected node has the host's focus,
  as a HottyDiff's hunk does, so the host scrolls it into view.
- "Files don't have icons": the storybook pane still ran the build from
  before HottyIcon. Relaunched.
- "Why do we limit the height?" The story set `height: 12` to show the
  scrolling, while the pane had room for all of it. The story has no
  height now. A tree that fills the room its column has, and scrolls
  only past that, needs the layout to give it a height (a `weight` in a
  Column whose surface the program sizes): it's the storybook nav's need
  too, so it comes with that leg.
