# 2026-10-18.5 — KIT-PICKER: the query is a text input, its caret an input's

The maintainer, of the picker's query: "Why did you decide to put custom
block cursor instead of using default a2ui input with blinking cursor? I
want the default one."

Two things made it a block:
- **On a host** the query was text in a focusable box, the program
  editing it and drawing a `k-caret`. That was to dodge SPEC §6.2, under
  which a host leaves a focused field's value alone while plx rewrites its
  query (Tab's completion, a staged command).
- **In cells** the kit draws a text field's caret as a block under a
  terminal's keymap (profile §3.5), which plx sets.

**Now:**
- **Host:** the query is an `input` (`k-pick-input`) the host edits, its
  caret the host's own, blinking. Its `data-keys` give the program the
  picker's keys (`pickKeys`): the moves, the actions' keys, the panel's.
- **The query the program writes:** a query written other than as the
  user typed it (`view.Pick.Typed`, `Written`) comes in a new `input`,
  its id `~h<n>`. A new id is a new element (SPEC §6.2's step 3), so the
  host has the value; the keyboard follows it (`focusOn`), and the
  typed-value bookkeeping (`holdEdit`, `resend`, `edited`) knows it as
  the picker's field (`fieldDOM`). The program's own editing of the
  query on a host (`pickEdit`) is gone.
- **Cells:** the caret is the terminal's own cursor whatever the keymap,
  always there while the picker has the keyboard; the terminal blinks it.

**Checked:** the gate; TestPickerOnHost (typing in the host's input
reaches `/q`; a written query comes in `~h1`, which has the keyboard); the
vectors on both renditions; the page in Chromium.

Profile §2, §6.32.
