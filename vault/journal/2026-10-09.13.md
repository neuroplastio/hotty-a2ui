# 2026-10-09.13 — KIT-06c: HottyDiff

The eighth phase-1 leg: a change to code, as a review shows it. Bubble
Tea has no diff, so the reference is OpenTUI's Diff, a Bun program in
`ref/opentui` that `make shot NAME=diff` now runs (`ref-shot.sh` takes
an OpenTUI reference where `ref/opentui/NAME.ts` exists). OpenTUI's
takes a patch of one file and has no file names, folds, word marks or
selection. It rejected the story's first patch: both Go hunk headers
counted a line more than they held, which the kit's parser had let
through. The story's patch is fixed.

**Package `diff`:**
- `Parse` reads a patch: git's (renames, new and deleted files, binary
  files) or diff -u's, with or without file headers. A hunk cut short
  ends where it stops. `Compare` diffs two texts with go-udiff's LCS
  (golang.org/x/tools' internal diff), into hunks with `context` lines
  around each change.
- Each side of a hunk is highlighted as one text, so a multi-line
  string or comment lexes right; a line that doesn't come back whole is
  lexed alone. `Parse` and `Compare` cache their last 32 results by
  content, as `highlight` caches code.
- Changed words: in a run of removed lines followed by added ones, each
  removed line is set against the added line in its place. They are cut
  into words, runs of space and single other characters, and compared.
  A change that only inserts or only deletes slides as far right as the
  same words let it, and changes that then touch join. Without that,
  `{url}` → `{url} after {tries} tries` marked `} after {tries` and
  ` tries`. Lines with too little in common are marked whole, by delta's
  rule: what changed over the characters besides space, above 0.6.
  OpenTUI marks no words; delta and GitHub do.
- `Hunk.Skipped` is how many unchanged lines come before a hunk, and
  `File.After` how many follow the last one, where the diff knows (two
  texts).

**The catalog** (profile §6.13, instruction 13): `HottyDiff` has `patch`,
or `old`, `new`, `file` and `context`; `language`; `view` (unified or
split); `lineNumbers` and `wrap`, both on by default; `selected`;
`onActivate`; and `weight`. A hunk's id is `path:line`, its new side's
first line, so an agent can act on it: stage it, revert it, comment on
it.

**Cells:**
- A rail column, then for each file its name with `+N -M` (or new,
  deleted, binary). For each hunk, a `⋯ N unchanged lines` fold when it
  skips lines, its header in `info` with the section `muted`, then its
  lines: both numbers, the sign, the code.
- Split, where each side has room for 16 columns of code: old left, new
  right, ` │ ` between. A removed line sits beside the added line that
  replaces it; the shorter side is filled out with its line's tint.
- Tints: a sixth toward `error` or `success` for a changed line, a third
  for its changed words. Where the theme can't tint (the Terminal theme,
  ANSI-16, NO_COLOR), a changed line's text takes its role's colour, and
  its words are reversed too, as git's diff-highlight does. Two new cell
  fields carry that: `BackFg` and `BackAttr`.
- It's a list of hunks, as a Table is of rows. ↑ ↓ (k j) move between
  hunks, Home and End (g G) go to the ends, Enter or a second click acts.
  The selected hunk's rows have `▎` in the rail and its header reversed,
  in accent while it has the keyboard. A scroll view around it keeps
  that hunk in sight (`reveal`).

**HTML:**
- The same rows: token spans, `color-mix` tints, a grid of two columns
  for split.
- A hunk is a `role=option` block that reports clicks. While the diff
  has the keyboard, the selected hunk takes the host's focus, so that
  the host scrolls it into view (SPEC §5.3: focus scrolls an element
  into view). The box's `data-keys` give the program the arrows, Home,
  End and k j g G, which a scroll view around it would otherwise take.
- A split diff stays split on a host: the markup doesn't know the width,
  and Blitz has no container queries (media queries work, but they can't
  use the diff's own widths).

**Text:** a unified diff that patch reads: `---` and `+++`, hunks, signs.
