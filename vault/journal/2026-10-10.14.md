# 2026-10-10.14 — Round 1 review: the table's bar, code sideways, the viewport's fill

Three of the maintainer's round 1 notes
([feedback](../feedback/2026-10-10-review-round-1.md)), all in cells: the
table, code and viewport legs (KIT-01c, KIT-05c, KIT-07c). The html
rendition already does the last two its own way (a host scrolls code
sideways, and fills a scroll view with `--k-tonal`); the table's bar on a
host is the host's scrollbar, KIT-01h.

**Table** ("an indicator (small arrow) that there are more items in
either direction. Or a scrollbar (similar to viewport)"). The scrollbar,
since it already exists and says more than arrows: where the rows that
show sit, and how much is above and below. While the body scrolls, a
HottyScrollView's bar runs down it (`paintScrollbar`, the same glyphs and
roles: `┃` thumb in `muted`, in `accent` while the table has the keyboard,
on a faint `│` track), after a blank column past the last column's
padding. The rule runs over both columns and keeps its ` 1–7 of 12 `
counter. Tried first with the bar straight after the padding: the selected
row's reversed fill then ran into the thumb, and in the accent the two
read as one block. With the blank column the row ends, then the bar, as a
scroll view's content does. A table that scrolls is 2 columns wider
(natural width and minimum), and one that shows every row is as before.
Look: `scripts/ref-shot.sh table`.

**Code** ("User-agent line is clipped (but this is good, I expect
horizontal scroll here)"). A HottyCode with `wrap` off keeps cutting its
long lines with `…`, and now the wheel scrolls it sideways: its left and
right, or Shift with it (`storybook.WheelDelta` already turns that into
columns), six columns a notch, as a HottyScrollView's lines go. The gutter
stays put; a `…` stands in the code's first column while columns before
it are hidden, and in its last while more follow; the widest line's end
is as far as it goes, and a line that ends before the window shows
nothing. It needs no focus: the wheel finds the code under the pointer as
it finds a scroll view (the code registers in `scrolls` while its lines
are cut), and a code inside a scroll view goes first, while the wheel up
and down pass through it to the scroll view. Where it is scrolled is the
controller's state, `St.Left` by the code's key, as a scroll view's is,
and the element's `Left`. A host scrolled it sideways already
(`overflow-x: auto`).

**Viewport** ("Looks good, but some background separation could improve
it"). A HottyScrollView's box is filled with `surface`: each cell's
background all the way to it (`Back`, `BackMix` 255), unless its content
tinted it (a marked code line keeps its own). Where the theme has no
`surface` colour, nothing is painted: the Terminal theme today, until
stream S1 has it learn the terminal's colours. Seen filled, the text sat
against the fill's left edge, so the box gained a column of padding
before its content: content 3 columns narrower than the box (padding,
blank, bar), and the natural width and minimum 1 wider. Without a fill the
padding still sets the content in from its title. Look:
`bin/storybook -theme Nord -bare hotty/scroll`.

**Changed:** `rendition/cells/table.go`, `code.go`, `scroll.go`; one line
in `controls.go` (a table's natural width is `tableNatural`, with the
bar); `view/code.go` (`Left` from `St.Left`); profile §3.3 (natural widths
and minimums), §3.4 (HottyTable, HottyScrollView, HottyCode), §3.6 (the
fill), §3.7 (the wheel), §6.12. The scroll view tests and one diff test
moved a column for the padding.

**Open, for the maintainer** (proposals):
- The table's bar is a scroll view's; small ▲ ▼ arrows were the other way
  you named. Proposed to keep the bar, which matches the viewport.
- The viewport's padding column applies with or without a fill. Proposed
  to keep: the content stands in from its title either way.
- The code's sideways scroll has no key: it takes no focus, so as not to
  add a Tab stop per code block. With KIT-12's selection it could take
  focus and the arrows, as a scroll view does.
